# ADR 0006: Фиксация документа в чате Neural Assistant

- **Статус:** Accepted
- **Дата:** 2026-05-14
- **Автор:** Iakov
- **Область (Scope):** Neural Assistant (Frontend + Service)

## Контекст (Context)

На странице Neural Assistant есть три связанные зоны: список чатов, список документов и окно чата.
Нужно закрепить простой и прозрачный инвариант:

- если в чате есть хотя бы одно сообщение, документ для этого чата уже зафиксирован;
- после фиксации документа его нельзя менять для данного чата.

Без явного правила легко получить невалидные состояния (сообщения есть, а документ не определен) или изменяемый контекст уже начатого диалога.

## Варианты решения (Considered Options)

1. **Вариант А:** Фиксировать документ внутри первого `POST /chat` (один endpoint выполняет две операции).
2. **Вариант Б:** Использовать отдельный endpoint фиксации документа и выполнять его отдельно от отправки сообщения.

## Решение (Decision Outcome)

**Выбран Вариант Б.** Фиксация документа выполняется отдельным endpoint, а отправка сообщений остается отдельной операцией.

Целевая пользовательская последовательность:

1. Пользователь выбирает чат без сообщений.
2. Пользователь выбирает документ.
3. Чат становится доступен для ввода (сообщений пока 0).
4. Пользователь отправляет первое сообщение.
5. Документ фиксируется отдельным endpoint (однократно).
6. После фиксации документ больше нельзя менять.

Технический инвариант:

- если в чате есть минимум 1 сообщение, документ для чата зафиксирован на 100%.

### Обоснование (Pros)

- Простая ментальная модель: фиксация контекста отделена от отправки сообщений.
- Четкое разделение ответственности endpoint-ов.
- Понятный UX: смена документа доступна только до появления первого сообщения.
- Явная серверная проверка инвариантов предотвращает невалидные состояния.

### Недостатки (Cons)

- Появляется дополнительный вызов API.
- Требуется обработка ошибок фиксации и повторов на клиенте.

## Последствия (Consequences)

- Backend вводит endpoint однократной фиксации документа для чата.
- Backend запрещает состояния "есть сообщения, но нет зафиксированного документа".
- Frontend блокирует выбор документа, если в чате уже есть хотя бы одно сообщение.
- Frontend трактует возможность писать в чат как гарантию, что документ уже зафиксирован.

## План проверки (Verification Plan)

- **Сценарий А:** Чат без сообщений -> выбрать документ -> отправить первое сообщение -> фиксация успешна -> документ недоступен для смены.
- **Сценарий Б:** Попытка сменить документ после появления первого сообщения -> сервер возвращает ошибку/конфликт, UI не меняет документ.
- **Сценарий В:** Повторная фиксация того же документа -> идемпотентный успешный ответ.
- **Сценарий Г:** Попытка создать сообщение в чате с незафиксированным документом -> отклоняется сервером.

### Критерии успеха (Acceptance Criteria)

- [ ] Для чата с хотя бы одним сообщением документ всегда зафиксирован.
- [ ] Пользователь не может сменить документ после появления первого сообщения.
- [ ] API не допускает невалидное состояние "сообщения есть, documentId не зафиксирован".
