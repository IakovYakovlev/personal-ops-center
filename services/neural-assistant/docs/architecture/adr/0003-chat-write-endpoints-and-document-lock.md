# ADR 0003: Два write-endpoint-а для чата и фиксации документа

- **Статус:** Accepted
- **Дата:** 2026-05-14
- **Автор:** Jakov
- **Область (Scope):** neural-assistant

## Контекст (Context)

На странице Neural Assistant пользователь сначала выбирает чат и документ, затем пишет сообщения.
Ключевое правило домена: если в чате есть хотя бы одно сообщение, документ для этого чата уже зафиксирован и больше не меняется.

Без явного API-контракта есть риск смешения обязанностей, гонок и невалидных состояний вида "сообщения существуют, но documentId не зафиксирован".

## Варианты решения (Considered Options)

1. **Вариант А:** Выполнять фиксацию документа и запись первого сообщения в одном endpoint-е.
2. **Вариант Б:** Разделить операции на два endpoint-а: отправка сообщения и фиксация документа.

## Решение (Decision Outcome)

Выбран Вариант Б.

В API фиксируются два write-endpoint-а:

1. **POST /chat** — добавляет сообщение в существующий chatList.
2. **PATCH /chat-list/:chatListId/document-lock** — однократно фиксирует documentId для chatList.

Серверный инвариант:

- наличие хотя бы одного сообщения в чате означает, что documentId у chatList зафиксирован;
- после фиксации documentId не может быть изменен на другое значение.

Рекомендованный пользовательский поток:

1. Выбрать чат без сообщений.
2. Выбрать документ.
3. Отправить первое сообщение.
4. Вызвать endpoint фиксации документа (однократно).
5. После фиксации заблокировать смену документа.

### Обоснование (Pros)

- Простое разделение ответственности endpoint-ов.
- Логика домена читается напрямую по контракту API.
- Проще сопровождать и тестировать каждую операцию отдельно.
- Снижается связность между отправкой сообщений и привязкой документа.

### Недостатки (Cons)

- Добавляется дополнительный сетевой вызов.
- Нужна обработка конфликтов и повторов (idempotency) на клиенте.

## Последствия (Consequences)

- В сервисе появляется отдельная write-операция фиксации документа для chatList.
- POST /chat проверяет, что для чата выполняется доменный инвариант.
- PATCH document-lock должен корректно обрабатывать повторные вызовы:
  - повтор с тем же documentId считается успешным;
  - попытка изменить уже зафиксированный documentId возвращает конфликт.
- Frontend блокирует выбор документа после появления первого сообщения.

## План проверки (Verification Plan)

- **Сценарий А:** Чат без сообщений -> выбрать документ -> отправить первое сообщение -> зафиксировать документ -> документ заблокирован для изменений.
- **Сценарий Б:** Повторный PATCH с тем же documentId -> успешный идемпотентный ответ.
- **Сценарий В:** PATCH с другим documentId после фиксации -> 409 Conflict.
- **Сценарий Г:** Попытка иметь сообщения в чате при незакрепленном documentId -> отклоняется сервером.

### Критерии успеха (Acceptance Criteria)

- [ ] Для любого чата с сообщениями documentId всегда зафиксирован.
- [ ] Изменение documentId после фиксации невозможно.
- [ ] Два write-endpoint-а покрывают весь жизненный цикл: отправка сообщения и фиксация контекста документа.
